# JATOS-to-BIDS-pipeline

A Python pipeline for downloading, processing, validating, and structuring data from JATOS.

It can handle results from both OpenSesame and jsPsych, including malformed JSON structures from OpenSesame and different task versions within the same project.

## Overview

### `download.py`

Connects to a JATOS server, downloads all results, and structures the downloaded files.

### `validate.py`

Validates participant and study IDs within a project and allows the user to decide what to do with flagged results.

It also extracts specified variables from each task based on the schema mapping defined in `project_config.json`.

### `bidsify.py`

Takes the validated results and structures them according to the BIDS specification.

## Files

### `result_index.tsv`

Generated by `download.py`.

Contains metadata for each downloaded result.

### `validation_protocol.tsv`

Generated by `validate.py`.

Contains the result metadata from `result_index.tsv`, together with validation information and instructions for how each result should be handled.

### `project_config.json`

Created by the user.

Contains the schema mapping for each task and optionally all participant IDs that are part of a project. The IDs are used during validation.

See [project_config.json configuration](#configuration-project_config) for configuration.

### `.env`

Created by the user.

Contains information about the JATOS server and project root.

See [.env configuration](#configuration-env) for configuration.

## JATOS Study Naming Convention

To allow the pipeline to correctly identify the project, task, and task version, JATOS studies must follow specific naming conventions and the raw task data must contain certain variables.

### Task and Version

The task name and version must be stored in the raw data so that the pipeline can identify which mapping in `project_config.json` should be used.

The way this is done depends on whether the task was created with OpenSesame or jsPsych.

### OpenSesame

In OpenSesame, the first project object must contain the task name and version using the following naming convention:

```text
task-name v.x.x.x
```

For example:
```text
AACT v.1.0.0
```
The version is used by the pipeline to select the correct mapping from project_config.json.

### jsPsych

In jsPsych, the task name and version must be stored in a variable in the raw data.

For example, create a variable called title:
```JavaScript
const test_version = "AACT v.1.0.0";
```

The variable must then be stored in a trial so that jsPsych includes it in the result data.

The variable used to store the task name and version must also be added to config.py under the Title keys comment.

For example, if the variable is called `test_version`, add it to the title keys:
```python
# Title keys
TITLE_KEYS = ['test_version']
```

The exact variable name used in config.py must match the variable stored in the jsPsych result data.

### JATOS Study Name

JATOS studies should follow this naming convention:

[PROJECT-NAME]_arm-[ARM]_ses-[SES]_task-[TASK]

For example:

SELMA_arm-UPP_ses-01_task-AACT

The individual components are:

| Component | Description |
|---|---|
| `[PROJECT-NAME]` | The name of the project that the task belongs to. |
| `arm-[ARM]` | Identifies a specific arm of the project. The pipeline does not currently use the arm, but it can be useful for distinguishing between different data collections, such as different laboratories or locations. |
| `ses-[SES]` | Identifies the session. This can be used when a participant completes the same task during a follow-up session. The session can be a number or a string. |
| `task-[TASK]` | The name of the task. The task name should not include the version. |

For example, a project with data collected at two different locations could use:

SELMA_arm-UPP01_ses-01_task-AACT
SELMA_arm-KAR01_ses-01_task-AACT

If the same participant completes the task again during a follow-up session:

SELMA_arm-UPP01_ses-01_task-AACT
SELMA_arm-UPP01_ses-02_task-AACT

The task version should not be included in the JATOS study title. The version is instead stored in the raw task data and is used to select the appropriate version-specific mapping from project_config.json.

## Validation

The `validate.py` script creates a `validation_protocol.tsv` file containing the same data as `result_index.tsv`, with four additional columns:

| Column | Description |
|---|---|
| `id_not_in_project` | Indicates whether the participant ID is not part of the project. |
| `duplicate_id` | Indicates whether the participant ID occurs more than once for the same study. |
| `action` | Specifies what should be done with the result. |
| `argument` | Contains an additional argument required by some actions. |

### Automatic Validation

The `id_not_in_project` and `duplicate_id` columns are automatically checked and populated with boolean values.

#### `id_not_in_project`

For this check to be performed, all participant IDs used in the project must be specified in `project_config.json`.

If a participant ID is found in the downloaded results but is not included in `project_config.json`, `id_not_in_project` is set to `TRUE`.

#### `duplicate_id`

`duplicate_id` is set to `TRUE` if there is at least one other row in `validation_protocol.tsv` with the same `study_id` and `participant_id`.

Otherwise, it is set to `FALSE`.

### User-Defined Actions

The `action` and `argument` columns are left blank for the user to specify how each result should be handled.

There are three possible actions:

| Action | Description |
|---|---|
| `keep` | Keeps the result. |
| `exclude` | Excludes the result. |
| `reassign_id` | Changes the participant ID. |

The `reassign_id` action requires an argument in the `argument` column. The argument should contain the new participant ID.

For example:

```text
action       argument
reassign_id  12345
```

## Configuration

<a id="configuration-env"></a>
### .env

Create a `.env` file in the `JATOS-to-BIDS-pipeline` directory.

The file must contain the following variables:

```dotenv
DOMAIN=https://ADDRESS-TO-JATOS-SERVER
API_TOKEN=jap_XXX
BASE_URL=${DOMAIN}jatos/api/v1/
PROJECT_ROOT=/path/to/project/root
```

Where:

| Variable | Description |
|---|---|
| `DOMAIN` | The URL of the JATOS server. |
| `API_TOKEN` | Your JATOS API token. |
| `BASE_URL` | The base URL for the JATOS API. This is constructed from `DOMAIN`. |
| `PROJECT_ROOT` | The root directory where project data will be stored. |

<a id="configuration-project_config"></a>
### project_config.json

The `project_config.json` file defines how data from different JATOS tasks and task versions should be processed. It can also optionally contain the participant IDs belonging to a project.

Create a `project_config.json` file in the `code/JATOS/` directory.

The configuration is organized into the following levels:


```text
task
  |
  └── version
        |
        └── mapping


project
  |
  └── ids
```
### Task

Each entry under task represents a task in JATOS.

For example:
```text
"AACT": {
```
The task name must match the task name stored in the JATOS result metadata.

### Version

Each task can contain one or more versions.

For example:
```text
"AACT": {
  "version": {
    "v.1.0.0": {
```
The version identifies the version of the task that produced the data.

Multiple versions can be defined for the same task. This is useful when a task has been modified during a project and the variable names have changed between versions.

For example:
```text
"AACT": {
  "version": {
    "v.1.0.0": {
      "mapping": {
        ...
      }
    },
    "v.1.0.0": {
      "mapping": {
        ...
      }
    }
  }
}
```
This allows the pipeline to process results from both versions using the appropriate mapping for each version.

### Mapping

The mapping section defines how variables in the raw JATOS data are renamed in the processed output.

For example:
```JSON
"mapping": {
  "pleasantVolume": "pleasant_volume",
  "rateReward": "rate_reward",
  "response_touch_response": "choice",
  "response_time_touch_response": "choice_rt"
}
```
The key on the left is the variable name as it appears in the raw JATOS data.

The value on the right is the variable name used in the processed data.

In other words:
```text
Raw JATOS variable           Processed variable
------------------           ------------------
pleasantVolume          ->   pleasant_volume
rateReward              ->   rate_reward
response_touch_response ->   choice
```
The pipeline looks for the variable on the left in the raw data and stores its value using the variable name on the right.

Handling Different Task Versions

Multiple mappings for the same task are useful when the task has been updated and variables have been renamed, added, or removed.

For example, suppose version v.1.0.0 of a task contains:
```JSON
"mapping": {
  "response_touch_response": "choice"
}
```
Later, the task is updated to version v.2.0.0 and the variable is renamed:
```JSON
"mapping": {
  "response": "choice"
}
```
Both versions can be defined in project_config.json:
```JSON
"my_task": {
  "version": {
    "v.1.0.0": {
      "mapping": {
        "response_touch_response": "choice"
      }
    },
    "v.2.0.0": {
      "mapping": {
        "response": "choice"
      }
    }
  }
}
```
The pipeline then uses the mapping corresponding to the version of the task that produced each result.

This makes it possible to process data from different versions of the same task into a consistent output format.

### Project IDs

The project section of project_config.json can be used to specify all participant IDs that belong to a project.

These IDs are used by validate.py to determine whether a result belongs to the project.

For example:
```JSON
{
  "project": {
    "SELMA": {
      "ids": [123, 456, 789, 101, 102]
    }
  }
}
```
The project name is used to identify the project, and the ids list contains all participant IDs that are expected to be part of the project.

During validation, each participant ID in the downloaded results is compared against this list.

If an ID is found in the downloaded results but is not included in the project's ids list, the id_not_in_project column in validation_protocol.tsv is set to TRUE.

For example, if the configuration contains:
```JSON
{
  "project": {
    "SELMA": {
      "ids": [123, 456, 789]
    }
  }
}
```
and a downloaded result contains participant ID 999, the result will be flagged:

participant_id    id_not_in_project
123               FALSE
456               FALSE
999               TRUE

The project section is optional. If no project IDs are specified in project_config.json, the id_not_in_project validation cannot be performed.

### Example

A complete configuration for a task with two versions and a list of project IDs could look like:

```json
{
  "task": {
    "AACT": {
      "version": {
        "v.1.0.0": {
          "mapping": {
            "ID": "ID",
            "pleasantVolume": "pleasant_volume",
            "unpleasantVolume": "unpleasant_volume",
            "rateReward": "rate_reward",
            "response_touch_response": "choice",
            "response_time_touch_response": "choice_rt"
          }
        },
        "v.2.0.0": {
          "mapping": {
            "ID": "ID",
            "pleasantVolume": "pleasant_volume",
            "unpleasantVolume": "unpleasant_volume",
            "rateReward": "rate_reward",
            "response": "choice",
            "response_time": "choice_rt"
          }
        }
      }
    }
  },
  "project": {
    "SELMA": {
      "ids": [123, 456, 789, 101, 102]
    }
  }
}
```
The important concept is that the right-hand side defines the standardized output variable names, while the left-hand side defines where the pipeline finds those variables in the raw JATOS data.

The project section is optional. If included, the ids list contains all participant IDs that belong to the project and is used by validate.py to identify results with IDs that are not part of the project.

## Installation

### Requirements

This project requires:

- Python 3.12.13
- `pip`
- `venv`

### 1. Clone the repository

Clone the repository and navigate into the project directory:

```bash
git clone <repository-url>
cd JATOS-to-BIDS-pipeline
```
### 2. Create a virtual environment:

```bash
python3 -m venv .venv
```
### 3. Activate the virtual environment

On Linux and macOS:
```bash
source .venv/bin/activate
```
On Windows:
```PowerShell
.venv\Scripts\Activate.ps1
```
### 4. Install dependencies

With the virtual environment activated, install the required Python packages from requirements.txt:

```bash
pip install -r requirements.txt
```
5. Configure the environment

Create a .env file in the JATOS-to-BIDS-pipeline directory.

See the [`.env` configuration](#env) section for information about the required variables.

## Usage
### Command-line arguments

Both `download.py` and `validate.py` support the following argument:

| Argument | Description |
|---|---|
| `-s`, `--studies` | One or more studies to download or validate. If omitted, all studies are processed. |

### Example

To download one or more specific studies:
```Bash
python download.py --studies STUDY_NAME
```
Multiple studies can be specified:
```Bash
python download.py --studies STUDY_NAME_1 STUDY_NAME_2 STUDY_NAME_3
```
